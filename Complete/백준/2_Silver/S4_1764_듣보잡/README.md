## 🔗 문제 링크

[백준 1764번 - 듣보잡](https://www.acmicpc.net/problem/1764)

**난이도**: Silver 4

---

## 🤔 접근법

(성공 후, 부분적인 최적화 진행)

'듣도 못한 사람'과 '보도 못한 사람'의 **교집합**을 구하는 문제.

N명의 듣도 못한 사람과 M명의 보도 못한 사람 중 **둘 다 해당하는 사람**을 찾아야 함.

**핵심**: 해시 테이블(`unordered_set`)을 사용하여 O(1) 시간에 존재 여부 확인!

---

## 💡 정답 풀이 방법

**알고리즘**: 해시 테이블(unordered_set) + 벡터 정렬

**핵심 아이디어**:
```
1. 듣도 못한 사람 N명을 unordered_set에 저장

2. 보도 못한 사람 M명을 순회하며 set에 존재하는지 확인

3. 존재하면 결과 벡터에 추가

4. 결과 벡터를 사전순 정렬 후 출력
```

---

## 🔑 핵심 포인트

### 1️⃣ unordered_set으로 O(1) 조회

```cpp
unordered_set<string> unSet;

// 듣도 못한 사람 저장
for (int i = 0; i < n; ++i)
{
    cin >> temp;
    unSet.emplace(temp);  // O(1) 평균
}

// 보도 못한 사람 중 교집합 찾기
for (int i = 0; i < m; ++i)
{
    cin >> temp;
    if (unSet.find(temp) != unSet.end())  // O(1) 평균
    {
        v.emplace_back(temp);
    }
}
```

**✅ 핵심**:
- `unordered_set`은 해시 테이블 기반으로 평균 O(1) 조회
- `set`은 Red-Black Tree 기반으로 O(log N) 조회
- 이 문제에서는 `unordered_set`이 더 효율적!

### 2️⃣ find vs count

```cpp
// 방법 1: find 사용 (현재 코드)
if (unSet.find(temp) != unSet.end())

// 방법 2: count 사용 (더 간결)
if (unSet.count(temp))  // 있으면 1(true), 없으면 0(false)
```

**✅ 핵심**: 성능은 동일, `count`가 더 간결함

### 3️⃣ 결과 정렬

```cpp
sort(v.begin(), v.end());  // O(K log K), K는 결과 개수
```

**✅ 핵심**:
- 문제에서 사전순 출력을 요구
- ★ 결과만 정렬하면 되므로 전체 데이터를 정렬하는 것보다 효율적

### 🔬 reserve() 사용 시 성능 변화

```cpp
unSet.reserve(500004);  // 해시 버킷 미리 할당
v.reserve(500004);      // 벡터 공간 미리 할당
```

```
메모리: 26484 KB (약 3.5배 증가!)
시간: 20 ms (약간 감소)
```

### ❓ 왜 메모리가 3.5배나 증가할까?

**unordered_set::reserve(500004) 영향**:
```
┌─────────────────────────────────────────────────────┐
│  해시 버킷 배열 미리 할당                            │
│  500,004개 버킷 × 포인터 8바이트 ≈ 4MB              │
│  + 해시 테이블 메타데이터 + 로드팩터 여유분          │
│  → 총 약 10MB 이상 사용                             │
└─────────────────────────────────────────────────────┘
```

**vector::reserve(500004) 영향**:
```
┌─────────────────────────────────────────────────────┐
│  연속 메모리 블록 미리 할당                          │
│  sizeof(string) = 32바이트 (MSVC 기준)              │
│  500,004 × 32B ≈ 16MB                              │
└─────────────────────────────────────────────────────┘
```

**💡 결론**: 데이터 크기를 정확히 모르면 reserve 안 하는 게 이득!

※ 이 문제의 경우 최대 범위 50000까지 들어 올지? 안 들어 올지? 모름! 

=> 메모리는 과하게 낭비, 시간 약간 빨라짐.

※ 반대로, 50000 무조건 들어오고, 줄어들고 늘어나고를 반복하면, 미리 할당이 좋을 수 있음.

=> 재할당 방지로 인해, 속도 증가.

## 🔧 추가 최적화 포인트

### 1️⃣ for 루프에서 복사 방지

```cpp
// 현재 코드 (복사 발생)
for (auto name : v)
{
    cout << name << '\n';
}

// 최적화 코드 (참조 사용 - 복사 없음)
for (const auto& name : v)
{
    cout << name << '\n';
}
```

### 📋 auto vs auto& vs const auto& 비교

| 구분 | 동작 | 원본 수정 | 메모리 | string 비용 |
|------|------|----------|--------|------------|
| `auto` | **복사** 생성 | ❌ 불가 | 새 객체 생성 | 복사 발생 (느림) |
| `auto&` | 참조 | ✅ 가능 | 추가 없음 | 없음 |
| `const auto&` | 읽기 전용 참조 | ❌ 불가 | 추가 없음 | 없음 |

**✅ 권장**: 읽기만 할 때는 `const auto&` 사용!

## ⏱️ 시간복잡도

**전체 시간복잡도**: **O(N + M + K log K)**

**상세 분석**:
```
1. 듣도 못한 사람 저장 : O(N)
   - N번 반복
   - 각 삽입 O(1) 평균

2. 보도 못한 사람 조회 : O(M)
   - M번 반복
   - 각 조회 O(1) 평균

3. 결과 정렬 : O(K log K)
   - K = 듣보잡 수 (교집합 크기)
   - K ≤ min(N, M)

총합 : O(N + M + K log K)
```

**시간 제한 체크**:
- N, M ≤ 500,000
- 최악: 500,000 + 500,000 + 500,000 × 19 ≈ 1,050만 연산
- **1,050만 연산** < **1억** → 시간 내 통과 가능 ✅

---

## 💾 공간복잡도

**O(N + K)**
- `unSet` : N개의 문자열 저장
- `v` : K개의 결과 문자열 저장
- K ≤ min(N, M)
